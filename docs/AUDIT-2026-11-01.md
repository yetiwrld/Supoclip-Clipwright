# Technical audit and corrections — 2026-11-01

Scope: the six points raised after the initial transformation. Everything below
was executed in this environment; anything that could not run is marked
**NOT RUN** with the reason and the exact command to run it on the target
machine.

Environment of this audit: Linux sandbox, **no** Docker, **no** Ollama daemon,
**no** NVIDIA/AMD GPU, no internet except a package allowlist. FFmpeg 7.0.2 and
FFprobe (static builds from the npm/PyPI registries) and OpenCV 4.13 (the version
the project pins) were installed to run the render tests. Those three are tools,
not the AI models.

---

## 1. Windows → Docker Ollama connectivity

**What was wrong.** The compose file already pointed the services at
`http://host.docker.internal:11434/v1` and set `extra_hosts:
host.docker.internal:host-gateway` on `backend`, `worker` and `ai-worker`. That
part was right. What was missing was (a) a way to prove each container can
actually reach the daemon, and (b) any guidance for the real-world failure:
native Ollama binds `127.0.0.1:11434`, which a container can never reach.

**Corrections**

| File | Change |
|---|---|
| `backend/src/local_ai.py` | New `storage_status()` (uploads/clips/models/whisper probes, checkpoint *readability*, not just `is_file()`), `probe_components()`, `verify_exit_code()`, `_render_report()` and `main()`, so `python -m src.local_ai --check` runs the full readiness probe inside the process it is executed in. |
| `scripts/verify_local_ai.py` *(new)* | Runs that probe via `docker compose exec -T` in `backend`, `worker` and `ai-worker`, prints a component × service matrix, attributes each failure to its service (`worker: ollama_reachable`), and adds the host-side listener check that explains the usual cause. Exits 2 when Docker is absent, 1 when any running service is not ready. |
| `scripts/setup-ollama-windows.ps1` *(new)* | `-Check` (read-only), `-Configure` (user `OLLAMA_HOST=0.0.0.0:11434`, restart, one inbound rule restricted to the Docker/WSL subnet on the **Private** profile), `-UseDockerOllama` (compose profile, models in `./data/ollama`, `OLLAMA_BASE_URL=http://ollama:11434/v1`), `-RemoveFirewallRule`. Never touches the Public profile, `Any` remote address, port forwarding or `netsh`. |
| `docker-compose.yml` | Ollama profile host port is now `${OLLAMA_HOST_PORT:-11434}` so it cannot collide with a native daemon; frontend gets `OFFLINE_MODE` and a read-only `/config` mount. |
| `docs/local-ai.md` | New "Windows: making native Ollama reachable from Docker" section with the safe procedure and the in-container verification commands. |

**Can Docker reach Ollama from all workers?** The *implementation* is in place
for all three services (same base URL, same `extra_hosts`, same probe), and the
probe logic is covered by tests against a real loopback HTTP server. The actual
container→host path **was not executed here** — Docker does not exist in this
sandbox. Command to run on the Windows machine:

```powershell
docker compose up -d
powershell -ExecutionPolicy Bypass -File scripts\setup-ollama-windows.ps1 -Check
python scripts\verify_local_ai.py
```

## 2. Setup verification

`scripts/setup_local_ai.py --check` now ends with a **container verdict** and
refuses to report readiness when the containers have not confirmed anything:

* `run_container_verification()` calls `verify_local_ai.py --json` and returns
  `(True|False|None, detail)`. `None` ("Docker not running") is printed as a
  warning and **never** counts as ready; the exit code is non-zero.
* The backend probe checks, per service: Whisper checkpoint present,
  checkpoint *readable*, Ollama reachable, configured model installed and
  usable, FFmpeg **and** FFprobe, uploads/clips/models/whisper directory
  writable, and offline-mode state.
* Failure text names the component and the fix (`ollama pull llama3.2:3b`,
  `python scripts/setup_local_ai.py --whisper-model small`, or the compose mount
  that is wrong).

Verified here: with no Docker, `setup_local_ai.py --check` prints
`Containers: Docker Compose is not running; containers were not verified` and
`Not ready for offline processing yet`, exit code 1 — it no longer claims
readiness from host facts.

## 3. Offline mode disables telemetry

Every integration was located and gated on the **runtime** switch (not just a
build-time key):

| Surface | Gate |
|---|---|
| DataFast (`/js/script.js`, queue stub, `track`, `identify`) | `layout.tsx` renders nothing unless `analyticsDecision().allowed`; `lib/datafast.ts` returns early without `data-analytics="on"` |
| Tilly (`tilly.samihindi.com`) | same layout decision |
| PostHog browser SDK + session replay | `instrumentation-client.ts` initialises only when the server marked the document `data-analytics="on"` |
| PostHog error capture (`error.tsx`, `global-error.tsx`, `captureApiFailure`, `resetAnalytics`) | `isClientAnalyticsEnabled()` |
| PostHog server SDK (`instrumentation.ts` request errors) | `getPostHogServer()` returns `null` while offline |
| PostHog Python (backend exception handler) | `get_posthog_client()` returns `None` while offline |
| DataFast/PostHog reverse proxies (`/js/script.js`, `/api/events`, `/ingest/*`) | `next.config.ts` registers no rewrites unless `OFFLINE_MODE=false` |
| Campaign attribution | `AttributionTracker` not rendered while offline |

The decision is re-read from the same `offline-mode.json` the Settings switch
writes, on every request.

Verified live against the dev server: with offline mode on, the served HTML has
**no** `data-analytics="on"`, no DataFast/Tilly script tags and no `ingest`
proxy; with `OFFLINE_MODE=false` plus configured ids, all three appear again.

## 4. Integration testing — what actually ran

Executed on this machine:

```
$ PATH=<ffmpeg 7.0.2>/:<ffprobe>/:$PATH python scripts/local_workflow_test.py

[PASS] tools                  ffmpeg version 7.0.2-static
[PASS] import local video     source.mp4 1280x720 h264 40.0s 13455 KB
[SKIP] transcribe (Whisper)   the 'whisper' package is not installed (ModuleNotFoundError)
[SKIP] analyse (Ollama)       no transcript from Whisper to analyse
[SKIP] clip selection         synthetic demo window 2.0-22.0s (no local models available)
[PASS] cut clip               clean.mp4 20.00s in 4.24s
[PASS] open in editor         1 segment(s), 7 caption word(s), saved revision 1 to draft.json
[PASS] render/export          export-workflow-export.mp4 1080x1920 20.00s 5735 KB in 21.31s
[PASS] save + reopen          reloaded in a new process: 1 segment(s), 7 word(s), aspect vertical
[PASS] offline mode           on (env); hosted AI refused; ollama http://localhost:11434/v1

RESULT: 7 passed, 0 failed, 3 skipped
```

A second run with an older static FFmpeg build produced the same stages.

**Real, not simulated:** source generation, FFprobe inspection, the clip cut, the
application's `save_document`/`EditDocument`/`render_document` path, the burned-in
ASS captions, the 1080×1920 export and its FFprobe verification, and the reload
of the saved draft in a fresh interpreter (the file-level equivalent of an app
restart).

**Skipped, and why:**

* **Whisper** — the `whisper`/`torch` packages are not installed here, and the
  checkpoint download host is not reachable from the sandbox allowlist. No real
  transcription was performed.
* **Ollama** — no daemon and no model weights can be obtained here. No real
  model inference was performed.
* **Database/queue** — no PostgreSQL or Redis, so the full task pipeline
  (`POST /tasks` → worker → clips) was not exercised end to end; the editor and
  render layers it feeds were.

What *was* tested for Ollama is the client half, against real sockets: a threaded
HTTP server speaking `/api/tags` on loopback (`tests/unit/test_local_ai_probe_live_server.py`,
7 tests) covers reachability, model matching, malformed JSON, HTTP errors and the
"model missing" message.

## 5. Visual and branding recheck

* **Name** — the served landing/sign-in/blog/changelog/demo pages contain zero
  `SupoClip` occurrences; the only remaining instances in the repository are
  licence/attribution, upstream URLs, blog slugs and documented wire identifiers.
* **Logo** — every `<img>` uses `/brand/clipwright-logo.png` through
  `brand-mark.tsx`, carries `width`/`height`, `object-contain`, and
  `data-source-width/height="1254"`, so proportions cannot change. The asset is
  served byte-identical (1,057,282 bytes).
* **Dark theme** — `<html class="dark">` with `data-offline-mode="on"` on every
  served page; tokens in `globals.css` are the default; `.light` exists only for
  the optional toggle.
* **Light-background scan** — 43 raw `bg-white`/`stone`/`black` matches were
  triaged. They are contrast elements on media (play badge over a thumbnail,
  selected checkbox, white CTA on the share page), the floating library bulk-bar,
  and media placeholders. No light page background, card or form surface was
  found. These could be converted to tokens in a purely cosmetic pass; none of
  them produces a light surface in dark mode.
* **Title/metadata** — `<title>ClipWright Studio – Offline AI Video Clipper
  (Whisper + Ollama)</title>`, manifest 200, favicon 200, apple-touch and PWA
  icons served from `/brand/`.

## 8. Honest status

Local **rendering, editing, export, project persistence and the offline privacy
switch** are verified here. Local **Whisper transcription** and **Ollama
inference**, the **container↔host network path** and the **full pipeline with
PostgreSQL/Redis** are implemented, unit-tested and instrumented, but were **not**
executed, because this environment has no Docker, no PostgreSQL, no Ollama and no
route to the model downloads. Until `scripts/verify_local_ai.py` and
`scripts/local_workflow_test.py` pass on the Windows machine, offline
compatibility is not claimed.
